# Test Ideas: Secure Document Upload

Test ideas are grouped by quality characteristic, then by the acceptance criterion they probe.

## Functionality

**File format support**
- Upload valid PDF, DOCX and TXT files and confirm each is accepted and stored intact.
- Upload unsupported formats (.exe, .zip, .jpg, .doc, .rtf, .odt, .xlsx) and confirm clear rejection.
- Rename a file to fake its type (e.g. malware.exe renamed to contract.pdf). The system should validate real content (magic bytes/MIME), not just the extension.
- Test extension edge cases: uppercase (.PDF), double extensions (report.pdf.exe), no extension, trailing dots or spaces, and a bare ".pdf".
- Upload a PDF that is password-protected, corrupted, or zero-byte, and a DOCX that is macro-enabled or truncated.
- Upload a TXT in different encodings (UTF-8, UTF-16, ANSI) and with non-Latin characters.

**File size limit**
- Boundary values: 19.99MB, exactly 20MB, 20MB + 1 byte, and 0 bytes. Also clarify whether 20MB means 20,000,000 or 20,971,520 bytes.
- Confirm the error message for oversized files is clear and that rejection happens early (client-side check and server-side enforcement).
- Bypass the client-side check (modify the request or call the API directly) to confirm the server still enforces the limit.
- Send a request whose declared Content-Length is smaller than the actual body size.

**Progress feedback**
- Verify progress is displayed and moves monotonically from 0 to 100% for small, medium and large files.
- Confirm that 100% is only shown once the file is fully stored and validated, not merely transmitted.
- Test progress behavior on slow, throttled, and intermittent connections.
- Cancel an upload mid-way and confirm that progress stops, partial data is cleaned up, and the user is told.
- Upload several files at once and check that progress is tracked per file.
- Verify the failure state is shown (not stuck at 99%) when the upload errors out.

**Upload workflow robustness**
- Interrupt the upload (close tab, lose network, session timeout, server restart) and check for retry/resume behavior and no orphaned files.
- Upload files with special characters, very long names (255+ chars), spaces, and Unicode/emoji in filenames.
- Upload two files with the same name, and the same file twice, and check for overwrite, versioning or duplicate handling.
- Click the upload button repeatedly or double-submit the form.

**Audit report**
- Confirm an audit entry is created for every attempt, both successful and failed (rejected format, too large, network failure, virus detected).
- Check that entries contain the right content: user, timestamp, filename, size, outcome, and failure reason.
- Verify the audit entry is created even when the upload is cancelled or aborted midway.
- Check the audit record's outcome always matches what actually happened (no "success" entry for a file that wasn't stored).

## Data Integrity

- Upload a file, download it, and compare checksums (SHA-256) to confirm the content is byte-for-byte identical.
- Verify that content, formatting, embedded fonts, images and metadata in PDF/DOCX are preserved with no corruption or conversion.
- Confirm no truncation occurs for files at or near the 20MB limit.
- Upload multiple files concurrently from different users with identical names and confirm no cross-contamination or overwriting.
- Simulate failures mid-upload (storage full, database down, network drop) and check that no partial or corrupt file is left accessible, and that the database record and stored file stay consistent (no record without file, or file without record).
- Check that the audit log is tamper-evident and cannot be edited or deleted by the uploader, and that entries remain consistent with the stored file state.
- Verify timestamps in the audit trail are accurate and consistent across time zones.
- Check that file metadata (uploader, upload time, original filename, size) is stored accurately.
- Verify encoding of special characters in filenames survives storage and retrieval.
- Test that deleting or replacing a document keeps the audit history consistent.
- Verify that stored files are protected against silent corruption (checksum verification on read, backups).

## Security

**Access control**
- After upload, confirm that only the uploader can access the document: test with another paralegal, an admin, a user in the same team, and an unauthenticated user.
- Attempt direct URL access (IDOR): change document IDs in the URL or API to guess other users' documents.
- Test that links to documents can't be accessed after logout, session expiry, or when a token is reused.
- Check that search, listing, thumbnails/previews, and API endpoints don't leak documents or metadata (filenames, sizes) to other users.
- Verify the default permission is private even if the upload was done via API, bulk upload or a different client.
- Confirm that sharing is only possible through an explicit action by the owner and that revoking access takes effect immediately.
- Check that permissions can't be escalated through parameter tampering (e.g. adding an "owner" or "visibility=public" field in the upload request).

**Malicious file handling**
- Upload files containing malware (use the EICAR test file) and confirm they're scanned, quarantined or rejected, and the event is logged.
- Upload PDFs with embedded JavaScript, DOCX with macros or external links, and zip bombs or decompression bombs disguised as DOCX (which is a zip).
- Upload files with XXE payloads in DOCX XML, and polyglot files (valid as two formats).
- Try path traversal in filenames (../../etc/passwd, ..\\windows) and null bytes in filenames (file.pdf%00.exe).
- Upload a TXT or file name containing HTML/script (XSS) payloads and check they're sanitized when rendered in the UI or audit log.
- Test SQL/command injection via filename and metadata fields.
- Confirm uploaded files are stored outside the web root, with a non-executable content type, and are served with safe headers (Content-Disposition, X-Content-Type-Options: nosniff).

**Transport, storage and authentication**
- Confirm uploads are only possible over HTTPS and that TLS configuration is sound; verify HTTP requests are rejected or redirected.
- Verify files are encrypted at rest and that storage locations (e.g. cloud buckets) aren't publicly accessible or listable.
- Attempt upload without authentication, with an expired token, a tampered token, and with a role that lacks upload permission.
- Test CSRF protection on the upload endpoint.
- Check for rate limiting and abuse protection (many rapid uploads, large uploads to exhaust storage or bandwidth, denial of service).
- Verify error messages don't leak internal paths, stack traces, or storage details.
- Check that sensitive content isn't exposed in logs, URLs, temp files, caches, or browser history, and that temp files are deleted after processing.
- Verify the audit log itself is access-controlled, since it contains filenames that may be confidential, and that it doesn't record document contents.
- Check compliance considerations for legal documents (data retention, privilege, jurisdiction of storage) and that deletion actually removes data from storage and backups.

## Questions to clarify with the team
- What exactly counts as "securely": encryption, malware scanning, access logs?
- Is the 20MB limit decimal or binary, and is it per file or per upload batch?
- Can admins or compliance officers access a user's documents despite the "only the uploader" rule?
- Should duplicate filenames be versioned or rejected?
- What should happen to the audit record if the user closes the browser mid-upload?
- Are multiple simultaneous uploads supported?

I'm happy to turn these into a prioritized risk-based test charter, or into formal test cases with steps and expected results.
